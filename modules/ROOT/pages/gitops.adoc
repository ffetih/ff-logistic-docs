= GitOps: how a change reaches the cluster
:description: Continuous delivery in FF Logistic: Git as the desired state, Argo CD pulling it into the cluster, Argo Rollouts releasing it by canary. What each part does, where it is in the repositories, and why it was chosen.

xref:delivery.adoc[Delivery] follows a change from a commit to an image: Maven, CI, packages. This page follows it from the image into the cluster. Nothing here pushes into the cluster: Git holds what should run, and the cluster pulls it.

[[picture]]
== The picture

[mermaid]
....
flowchart LR
  subgraph git["Git: the desired state"]
    RT["runtime<br/>charts, Applications,<br/>the switch"]
    IMP["modulith / services<br/>deploy/apps: values,<br/>image-local.yaml"]
  end
  DEV[developer] -->|pull request| CI[CI]
  CI -->|image| GHCR[(GHCR)]
  CI -->|commit: the new tag| IMP
  ACD[Argo CD<br/>in the cluster] -->|reads| RT
  ACD -->|reads| IMP
  OP[operator] -->|sync| ACD
  ACD -->|applies| K8S[ff-logistics namespace]
  K8S -->|pulls| GHCR
  RO[Argo Rollouts] -->|canary, analysis| K8S
....

CI has no access to the cluster: it holds no kubeconfig and runs no `kubectl`. Its last act is a commit. Argo CD, inside the cluster, reads Git and makes the cluster match it. This is the *pull* model; in a *push* model, the pipeline would deploy, and every pipeline would need the keys to the cluster.

[[principles]]
== The four principles, and how far this project follows them

GitOps is usually described by four principles (OpenGitOps):

[cols="2,3,1",options="header"]
|===
| Principle | Here | Followed

| *Declarative*: the system is described as the state it should be in, not as steps to get there
| Helm charts, kustomizations and Applications in runtime; values in each implementation's `deploy/apps`
| yes

| *Versioned and immutable*: that description is stored with its whole history, and what it names does not change
| Every change is a commit, reviewed in a pull request. Images are tagged with the commit they were built from (`image.tag: 7b75c9a…`), never `latest`
| yes

| *Pulled automatically*: agents fetch the description themselves
| Argo CD polls the repositories; the ApplicationSet looks again every 60 s
| yes

| *Continuously reconciled*: agents keep correcting the system towards the description
| The App of Apps does, with self-heal. The workloads do not: Argo CD shows their drift (`OutOfSync`), and an operator syncs
| partly, on purpose
|===

Why the last one only partly: a sync of a workload runs its database migration (a PreSync hook) and a canary, and the switch between implementations deletes one side's workloads. Here, a person decides when that happens. With self-heal on the workloads, a change merged at night would be live by morning, and the failure drill that stopped Kafka (xref:try-failures.adoc#kafka-down[drill 2]) would have been undone by Argo CD within seconds.

[[argocd]]
== Argo CD in this project

[cols="2,3,3",options="header"]
|===
| Concept | Where | What it does here

| *Application*
| `runtime/deploy/argocd/apps/*.yaml`
| One per platform part (postgres, kafka, keycloak, rustfs, identity, edge, argo-rollouts) and one per service of the active side.

| *AppProject*
| `project-ff-logistics.yaml`
| Limits the project's Applications to the five repositories they may read and to the `ff-logistics` namespace; the only cluster-wide kind they may create is a Namespace.

| *App of Apps*
| `deploy/argocd/root.yaml` (`ff-root`)
| One Application whose source is a folder of Applications. Adding a service is adding a file there, not running `kubectl`. It syncs on its own, with prune and self-heal: it holds Argo CD objects only, never workloads.

| *Argo CD managing itself*
| the `argocd` Application, `deploy/argocd`
| Argo CD's own installation (a pinned release, with local patches) is in Git too. An upgrade is a commit that changes the version, then a sync. Its objects carry `Prune=false`, so a mistake there cannot make Argo CD delete itself.

| *ApplicationSet*, matrix of two *git generators*
| `implementation.yaml` (`ff-implementation`)
| The first generator reads the switch (`active: services`), the second lists `deploy/apps/*` in the repository it names. One Application per folder, on the active side only. Both generators produce a `path`; `pathParamPrefix: switch` keeps the two apart.

| *Multi-source Application*, `$values`
| the ApplicationSet's template
| The chart comes from runtime, the values from the implementation's repository (xref:decisions.adoc#d8[decision 8]). The image tag lives next to the code that built it.

| *Helm value files, layered*
| `values.yaml`, `values-local.yaml`, `image-local.yaml`
| The last one wins. CI writes only `image-local.yaml`, so a person's settings and the bot's tag never touch the same file.

| *Sync waves*
| `argocd.argoproj.io/sync-wave: "-1"` on postgres, kafka, keycloak, rustfs and the project
| What others depend on is applied first, and must be healthy before the next wave.

| *Resource hooks*
| the chart's Jobs
| *PreSync*: create the database (weight -1), then migrate the service's own area. *PostSync*: a smoke test against the service. A failed PreSync Job stops the sync before any pod changes.

| *Resources finalizer*
| the ApplicationSet's template
| When the switch moves, the other side's Applications are no longer generated. Deleting them deletes what they deployed.

| *Sync policy*
| `syncPolicy` of each Application
| Automated with prune and self-heal for `ff-root`; manual for every workload (xref:#principles[above]). `CreateNamespace=true` where a namespace may not exist yet.

| *Health and sync status*
| the UI, `argocd app get`
| `Synced` / `OutOfSync` compares Git with the cluster; `Healthy` / `Progressing` / `Degraded` reads the resources themselves, including a Rollout's own health.
|===

[[rollouts]]
== Argo Rollouts: releasing by canary

Every service runs as a *Rollout*, Argo Rollouts' replacement for a Deployment, with a canary strategy (xref:walkthrough.adoc#s2[S2]):

[mermaid]
....
flowchart LR
  S[new image synced] --> W50["setWeight: 50<br/>one of two pods is the canary"]
  W50 --> A{"AnalysisRun<br/>GET canary:/actuator/health/release<br/>3 times, 10 s apart"}
  A -->|all UP| W100[setWeight: 100<br/>the canary becomes stable]
  A -->|one not UP| AB[abort:<br/>back to the stable version]
....

[cols="2,3",options="header"]
|===
| Concept | Here

| *Rollout*
| The chart renders a Rollout instead of a Deployment when `rollout.enabled`. `kubectl rollout status deploy/…` therefore finds nothing (xref:try-failures.adoc#lessons[a lesson from the drills]).

| *Canary and stable Services*
| `<service>` and `<service>-canary`; the analysis asks the canary directly, not through the gateway.

| *AnalysisTemplate*, web provider
| `<service>-release`: three reads, each `"UP"` or the release aborts (`failureLimit: 0`). The release group is a health group the service itself reports.

| *Abort*
| `FF_RELEASE_HEALTHY=false` makes a release report itself unfit: the canary is scaled away and the stable version keeps serving (xref:walkthrough.adoc#s2[a canary that aborts]).

| *Blue-green*
| Also in the chart (`strategy: blueGreen`, a preview Service, promotion by hand); the services use the canary.
|===

[[image-tag]]
== Who changes the image tag

After CI publishes an image, it commits the new tag to `image-local.yaml` in the same repository ("Publish image tags for …"). Argo CD then shows the Application `OutOfSync`, and a sync rolls it out.

The alternative is *Argo CD Image Updater*, which watches the registry and writes the tag itself. Here the CI that built the image also records it: one place that knows which commit became which image, and no extra component with write access to Git.

[[order]]
== The order things happen in

* *Within a sync*: waves first, lowest first; within a wave, hooks around the sync: PreSync Jobs, then the resources, then PostSync Jobs (xref:#ui-hooks[the anchored Jobs]).
* *Between Applications*: the platform before the services (waves -1 and 0), a service's API before its callers (routing before transportation in S5), and the edge last after a switch, so its smoke test checks the side that now answers (xref:switching.adoc#order-matters[order matters]).
* *Between repositories*: the build order of xref:delivery.adoc#order[Delivery], before anything reaches Git as a new tag.

=== The signs

[cols="1,3",options="header"]
|===
| Sign | Means

| green heart | *Health*: the resource itself is fine (pods ready, a Rollout finished, a Job succeeded). Read from the cluster.

[[ui-analysis]]
=== `AT` and `AR`: who judges a canary

An AnalysisTemplate is an *inspection form*; an AnalysisRun is *one inspection*, filled in for one release. The form is written once per service and synced from Git like any other resource. The Rollout controller fills in a new copy each time a release reaches its `analysis` step, and keeps it afterwards as the record. It is the same relationship as a class and its objects.

[mermaid]
....
sequenceDiagram
  participant R as Rollout routing
  participant AR as AnalysisRun
  participant C as routing-canary → the new pod
  R->>R: setWeight 50: one new pod, one old
  R->>AR: create from the template routing-release
  Note over AR: initialDelay 10 s
  loop count 3, interval 10 s
    AR->>C: GET /actuator/health/release
    C-->>AR: status UP
  end
  AR-->>R: Successful
  R->>R: setWeight 100: the new version is stable
....

The form, field by field (`templates/analysistemplate.yaml` of the `ff-service` chart):

[cols="2,2,4",options="header"]
|===
| Field | Here | Meaning

| `provider: web`
| `http://routing-canary.ff-logistics.svc.cluster.local.:8084/actuator/health/release`
| An HTTP GET from the Rollouts controller. Through the *canary* Service, so it reaches the new pods only, never the stable ones. The trailing dot makes the name absolute: without it, the DNS search domains cost 3–5 s on k3d.

| `jsonPath`, `successCondition`
| `{$.status}`, `result == "UP"`
| Take `status` from the body; a measurement passes when it is `UP`.

| `initialDelay`, `interval`, `count`
| `10s`, `10s`, `3`
| The first read 10 s after the canary is ready, then two more, 10 s apart: about half a minute.

| `failureLimit`
| `0`
| One `DOWN` fails the whole run.

| `timeoutSeconds`
| `5`
| A read with no answer is an *Error*, not a failure. A few in a row (`consecutiveErrorLimit`, 4 by default) also end the run.
|===

What the run's result does:

* *Successful*: the Rollout moves to its next step, `setWeight: 100`.
* *Failed*: the Rollout *aborts*. The canary is scaled to zero, the stable Service never stopped pointing at the old pods, and the Rollout, and with it the Application, is `Degraded`. Nothing in Git changes: the next sync of a fixed image starts a new release (xref:walkthrough.adoc#s2[a canary that aborts], S2).

A step, not a background: the `analysis` sits between two steps and blocks the release until it ends. The other kind, `strategy.canary.analysis`, runs alongside all the steps and aborts whenever it fails.

*What it asks, honestly*: the release group holds one indicator, a switch (`ff.release.healthy`, `FF_RELEASE_HEALTHY`). It shows the mechanism, a release that declares itself unfit; it does not measure how the canary behaves under traffic. A real analysis asks the metrics, for example the canary pod's share of `5xx` answers from Prometheus (`provider: prometheus`). That needs metrics first (xref:#not-yet[not yet]).

See the record of the last release:

[source,bash]
----
kubectl -n ff-logistics get analysisruns | grep routing
AR=$(kubectl -n ff-logistics get analysisruns --sort-by=.metadata.creationTimestamp -o name | grep routing | tail -1)
kubectl -n ff-logistics get $AR -o jsonpath='{range .status.metricResults[*].measurements[*]}{.phase} {.value} {.finishedAt}{"\n"}{end}'
----

The name is the Rollout, the new pods' template hash, the revision and the step index (`1`: the second step). Expect three lines, `Successful UP …`, 10 s apart.

[[ui-hooks]]
=== The anchored Jobs: PreSync and PostSync

A sync is a *move into a new flat*. *PreSync* is the work done before the furniture comes in: the schema the new code expects. The *sync* phase is the furniture: the ConfigMap, the Services, the AnalysisTemplate, the Rollout. *PostSync* is the walk through the flat once everything is in place: the smoke test.

A hook is a resource with the annotation `argocd.argoproj.io/hook`. Argo CD does not keep it in sync; it runs it at that moment of the sync and waits for it to finish. That is the anchor in the UI.

[mermaid]
....
flowchart LR
  P["PreSync<br/>routing-migrate--presync-…<br/>Flyway, then exits"] -->|Completed| S["Sync<br/>ConfigMap, Services,<br/>AnalysisTemplate, Rollout"]
  S --> C["Canary<br/>50 % → AnalysisRun → 100 %"]
  C -->|Healthy| Q["PostSync<br/>routing-smoke-test--postsync-…<br/>three checks"]
  Q -->|Completed| OK([sync Succeeded])
  P -->|Failed| F1(["sync Failed<br/>nothing applied, the old pods serve"])
  C -->|analysis Failed| F2(["Rollout aborted, Degraded<br/>PostSync never runs"])
  Q -->|Failed| F3(["sync Failed<br/>the new version stays: read the log"])
....

[cols="2,3,4,4",options="header"]
|===
| Hook | Job | What it does | If it fails

| PreSync, weight `-1`
| `<service>-database--presync-…`
| Creates the service's own database on the PostgreSQL server, if missing (`database.create`).
| Off for the business services: they all use `ff_logistics` (xref:decisions.adoc#d3[decision 3]). On for the analytics loader, the first application with a database of its own, `ff_logistics_analytics` (S6, xref:#ui-loader[below]).

| PreSync
| `<service>-migrate--presync-…`
| The service's own image with the Spring profile `migrate`: Flyway migrates the area's tables, records them in `<area>_flyway_history`, and the process exits.
| The sync fails before anything else is applied. No new pod ever starts on a schema it does not have.

| PostSync
| `<service>-smoke-test--postsync-…`
| `curl` in a shell script: readiness `UP`; `/api/v1/me` refused (`401`) without a token, `200` with one, for the tenant `ff-eu-freight`.
| The sync is marked `Failed`. Nothing is rolled back: the failure is the signal to look. `backoffLimit: 0`, because a smoke test that only passes on a second try has failed.

| PostSync
| `edge-smoke-test--postsync-…`
| The same kind of checks through the edge, after the edge Application's sync.
| As above.
|===

Four things that are easy to miss:

* *The migration runs while the old version serves.* The old pods keep taking traffic during PreSync and the canary, so a migration has to suit both versions: add, don't rename or drop in the same release. S05-05's `V4` adds a nullable column, `ecmr_document_uri`, which the old code never reads.
* *PostSync waits for the canary.* It runs once every resource is `Healthy`. A Rollout in its canary steps is `Progressing`, so the smoke test checks the version that already takes all the traffic. An aborted canary never becomes `Healthy`, so the test never runs on it.
* *A new name on every sync* (`generateName`): Argo CD watches this sync's Job, never one left from the sync before. Argo CD builds the name itself: the chart's prefix (which ends in a dash, hence the double dash), the hook type and the sync's time in Unix seconds. `transportation-smoke-test--postsync-1795221030` is the smoke test of the sync at 03:30:30 on 2026-11-21, Istanbul time. That is why the UI shows several anchored Jobs side by side, one pair per sync of the day, and why a name tells which sync made it.
* *Kubernetes deletes them, not Argo CD*: `ttlSecondsAfterFinished: 86400`, a day to read a failed run's log. The checks themselves are a plain ConfigMap with a tick, applied in the sync phase, so the PostSync Job reads the checks of the commit being synced.

Read the last two Jobs of a sync:

[source,bash]
----
for h in migrate smoke-test; do
  J=$(kubectl -n ff-logistics get jobs -l app.kubernetes.io/name=routing-$h --sort-by=.metadata.creationTimestamp -o name | tail -1)
  echo "== $J"; kubectl -n ff-logistics logs $J | tail -5
done
----

The migration's last lines name the versions it applied, or say the schema is up to date. The smoke test prints one `ok` line per check:

----
ok   sign-in as nexus.planner
ok   http://routing:8084 accepts connections
ok   GET /actuator/health/readiness (none): 200
ok   GET /api/v1/me (none): 401
ok   GET /api/v1/me (token): 200
----

[[ui-loader]]
=== analytics-loader: all three hooks

image::argocd/analytics-loader.png[analytics-loader: a Service, a Deployment with one pod, the smoke test's ConfigMap, and three anchored Jobs: database, migrate, smoke-test]

The first application with every hook the chart has (S6):

* *Three anchored Jobs from one sync*, in order: `database--presync` (weight `-1`) creates `ff_logistics_analytics` if it is missing, `migrate--presync` (weight `0`) runs the loader's own Flyway scripts in it, and `smoke-test--postsync` checks readiness once the pod is up. * *Not part of the switch*: no `ff-logistic/implementation` label. Like `identity`, it runs whichever side is active, because it reads the topics, not the code, of the side that sends them.
* *Synced to `2fce04f`, "Merge pull request #12 from ffetih/sprint/s06"*: the commit in runtime that added this Application. `and (1) more` is the values from shared, where the loader is built.
