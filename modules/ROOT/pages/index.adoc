= FF Logistic
:description: One logistics product, built as a modular monolith and as microservices, on one Kubernetes GitOps platform, and compared with measurements.

One logistics product, built twice: as a *modular monolith* and as *microservices*, on the same Kubernetes GitOps platform, behind the same switch, and then measured under load and failure.

== The question

"Should this be a monolith or microservices?" is usually answered by comparing a real system with an imagined one. Here both are real. The business rules are written once; only the wiring between the business areas differs. Both run against the same database tables, the same Kafka topics and the same identity service, and one Git commit decides which of them is running.

Think of one recipe book and two kitchens. In the first kitchen, every cook stands at the same counter: passing a dish is handing it over. In the second, each cook has a room of their own, and dishes go through hatches, with a ticket, sometimes late. The recipes are identical. What differs, and what this project measures, is everything about the hatches.

== Headline measurements

Five virtual users, four minutes measured against the edge, plus 60-second failure drills (xref:comparison.adoc[full comparison]):

[.kpi]

12.7 ms vs 20.1 ms

Flow 1 (`plan`) median latency — in-process call on modulith vs HTTP hop to routing on services (p95: 30.1 vs 44.5 ms).
****

[.kpi]
****
1,449 vs 2,413 MiB

Idle memory footprint — 4 modulith pods vs 7 service pods serving the identical API surface.
****

[.kpi]

Deliveries under a 60 s Kafka outage on both sides — transactional outbox drained cleanly once the broker returned.

16 s startup

Pod delete to last pod Ready on both sides, with zero-downtime canary rollouts and automated health analysis.

[quote]
____
_Bottom line:_ start with a *modular monolith* (~40% less idle RAM, ~37% lower cross-area latency, single-rollout changes); _earn your microservices when independent scaling, fault isolation, or team autonomy actually demands the cost_ (xref:comparison.adoc#takeaway[read the full verdict]).
____

== Engineering scope

[.pillar-grid]
--
[.pillar]
.Application Architecture & Backend
****
* *Hexagonal domain cores*: `standards`, `warehousing`, `transportation`, `routing` as reusable jars verified by Spring Modulith (`ApplicationModules.verify()`).
* *Event-driven consistency*: per-process transactional outbox (`ff-base-events`), Apache Kafka 4.2 (KRaft), idempotent consumers, dead-letter topics, and contract tests (`ff-contracts`).
* *Real logistics domain*: GS1 SSCC/GLN check digits, ISO 6346 containers, EN 16258 / ISO 14083 CO₂e footprint, Timefold route optimization with time windows.
* *Defense-in-depth multi-tenancy*: Keycloak facade + local JWKS, presigned write-once S3 (RustFS), PostgreSQL `FORCE RLS`, Superset guest tokens (xref:security.adoc[Security & Multi-Tenancy]).
****

[.pillar]
.GitOps, Progressive Delivery & Reliability
****
* *Declarative GitOps*: Argo CD App-of-Apps (`ff-root`) and a Matrix `ApplicationSet` (`ff-implementation`) that switches modulith ↔ services in one Git commit.
* *Progressive delivery*: Argo Rollouts canary releases with `AnalysisTemplate` health gates, PreSync database/Flyway Jobs and PostSync smoke tests.
* *Multi-repo CI/CD*: reusable GitHub Actions workflows across six repositories, GHCR image publishing, values kept next to code (xref:decisions.adoc#d8[decision 8]).
* *Observability & resilience*: OpenTelemetry + Jaeger 2.4 distributed tracing across HTTP and Kafka (xref:try-tracing.adoc[Try it: tracing]), plus repeatable k6 load scenarios and failure drills.
****
--

== Technology stack

[cols="2,5",options="header"]
|===
| Layer | Stack

| Language & Runtime | Java 25 (virtual threads), Spring Boot 4.1, Spring Modulith 2.1, Maven Wrapper
| Data & Analytics | PostgreSQL 17, Flyway (per-area history tables), PostgreSQL `FORCE RLS`, Apache Superset 4.1
| Reporting & Notifications | `shared/reporting` (`generation` + `delivery` modules), OpenHTMLToPDF (`pdfbox`), Mailpit SMTP, HTTP webhooks
| Messaging & Contracts | Apache Kafka 4.2 (KRaft), transactional outbox (`event_publication`), JSON contract tests (`ff-contracts`)
| Optimization & Storage | Timefold Solver (time windows), RustFS (S3-compatible, SigV4 presigned write-once links)
| Identity & Edge | Keycloak 26.8, dedicated Identity facade + JWKS, nginx single-origin console & gateway
| Observability & Delivery | OpenTelemetry, Jaeger 2.4, k3d, Argo CD 3.6, Argo Rollouts 1.10, Helm, Kustomize, GitHub Actions, GHCR, k6
|===
