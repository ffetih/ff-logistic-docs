= Architecture
:description: The layers, the repositories, one core with two wirings, the switch and the edge.

[[layers]]
== Three layers

Every part of the system sits in one of three layers, by a simple rule:

[cols="1,2,3",options="header"]
|===
| Layer | Rule | Contents

| *runtime* | What we run but do not write | k3d cluster, Argo CD, Argo Rollouts, PostgreSQL, Keycloak, Kafka, RustFS, Superset, the service Helm chart, the switch
| *shared* | What we write once; it does not care which implementation runs | The identity service, the analytics loader, the domain cores, the event contract
| *implementations* | The same business, wired two ways; exactly one is active | *modulith*: one Spring Modulith application. *services*: three Spring Boot services and a gateway.
|===

[mermaid]
....

  subgraph impl ["implementations: exactly one is active"]
    direction LR
    subgraph mod ["modulith"]
      APP["logistics-app<br/>one process"]

    subgraph svc ["services"]
      GW[gateway] --> WH[warehousing] & TR[transportation] & RO[routing]
    end
  end
  subgraph sh ["shared: written once"]
    direction LR
    DOM["domain cores<br/>standards · warehousing ·<br/>transportation · routing"]
    ID["identity<br/>Keycloak facade + JWKS"]

  EDGE --> impl

Whichever implementation is active reaches the platform the same way. Three things are true for both:

* *Only the identity service calls Keycloak.* The applications verify each token themselves, against the identity service's published keys (JWKS). Nothing on the request path waits for Keycloak.
* *Kafka does not feed Superset directly.* The analytics loader stores each delivery in its own database, which Superset reads as `analytics_reader`, one tenant at a time (row-level security).
* *Documents never pass through the applications.* They hand out presigned, write-once links; the browser or the driver's device talks to RustFS directly.

[[ports]]
== One core, two wirings

Each business area is a library, a _domain core_: its entities, rules, REST API and Flyway migrations. A core depends on `standards` and on nothing else of the business. When it needs another area, it declares a *port*: an interface for a question it asks (`DistanceLookup`), or an event it publishes (`ShipmentDelivered`). The two implementations differ only in the *adapters* that fulfil the ports.

[mermaid]
....
flowchart LR
  subgraph core ["transportation core: one jar, used by both"]
    API[ShipmentController] --> S[ShipmentService]
    S --> P{{"port<br/>DistanceLookup"}}
    S --> E{{"port<br/>events out"}}
  end
  subgraph m ["modulith adapters"]
    M1["calls routing's service<br/>in the same process"]
    N1["Spring Modulith event,<br/>listeners in the same JVM"]
  end
  subgraph s ["services adapters"]
    M2["HTTP to routing,<br/>timeout + haversine fallback"]
    N2["outbox row in the same<br/>transaction, then Kafka"]
  end
  P --> M1
  P --> M2
  E --> N1
  E --> N2
....

This is the classic ports-and-adapters (hexagonal) shape, used here for one specific reason: it isolates exactly the part that differs. A bug in a business rule is fixed once, for both sides. A difference in the measurements can only come from the wiring.

[[flows]]
== The flows between areas

In the earlier single-repository version, the business areas hardly talked to each other. Without flows between them there is nothing to compare, so three are part of the design:

[cols="3,1,2,2,1",options="header"]
|===
| Flow | Kind | Modulith | Services | Since

| A shipment delivered to a warehouse opens an inbound arrival there | event | Modulith event, through the outbox | Kafka, through the outbox | S4
| Transportation asks routing for a leg's road distance | query | method call | HTTP, timeout, haversine fallback | S5
| A completed route stop with proof of delivery delivers the shipment | event | Modulith event | Kafka through the outbox | S5
|===

Each flow goes through ports (xref:decisions.adoc#d2[decision 2]): the cores do not know each other. Transportation publishes `ShipmentDelivered`, in its own words; warehousing offers `InboundArrivals.open(ShipmentArrival)`, in its own. The *wiring* that translates one into the other is the only part written twice, and it is small: a listener in the modulith's `flows` module, a Kafka consumer in the warehousing service.

Both sides are eventually consistent: the delivery commits first, the arrival follows. What differs is the size of the window, and what can go wrong in it:

[cols="2,3,3",options="header"]
|===
| | Modulith | Services

| Between the two areas | a method call on another thread | a broker, a network, another process
| The listener fails | the row stays open; the outbox upkeep tries again later | the message is tried again, then goes to `….warehousing.dlt`
| Kafka is down | not involved | the row stays open in `transportation.event_publication`; the upkeep sends it once Kafka is back
| Delivered twice | possible (a retried row); the arrival opens once | possible (a resent row, a re-read message); the arrival opens once
|===

The outbox is the same library on both sides (ff-base-events, xref:decisions.adoc#d12[decision 12]); each process keeps it in a schema of its own.

[[flow-1]]
=== Flow 1, on each side

A question, not an event: a planner books a road leg by the coordinates of its two ends, and transportation asks routing for the distance before it saves the shipment. Transportation declares the question as a port, `DistanceLookup`; routing offers the answer as its API, `RoadDistances`. Neither knows the other.

[mermaid]
....
sequenceDiagram
  autonumber
  participant D as planner
  box modulith: one process
    participant T as transportation
    participant F as flows
    participant R as routing
  end
  D->>T: POST /api/v1/tms/shipments, a ROAD leg with its ends
  T->>F: DistanceLookup.roadKm(from, to)
  F->>R: RoadDistances.roadKm(from, to)
  R-->>T: km, from its road matrix
  T->>T: leg ROUTING; shipment saved
  T-->>D: 201 Created
....

[mermaid]
....
sequenceDiagram
  autonumber
  participant D as planner
  participant G as gateway
  participant T as transportation
  participant R as routing
  D->>G: POST /api/v1/tms/shipments, a ROAD leg with its ends
  G->>T: forward
  T->>R: GET http://routing:8084/api/v1/geo/distance, the planner's token
  alt routing answers within 1 s + 2 s
    R-->>T: {"distanceKm": ...}
    T->>T: leg ROUTING
  else no answer, an error, or too slow
    T->>T: the straight line x 1.24, leg ESTIMATE
  end
  T->>T: shipment saved
  T-->>D: 201 Created
....

The question is asked before any transaction starts, so no database connection waits for routing. What happens when routing cannot answer is decided once, in transportation's core: the straight-line estimate, and the leg says so (`distanceSource`: `GIVEN`, `ROUTING` or `ESTIMATE`). A shipment is never refused because routing is away. A leg booked by its ends is compared by its ends when the same order is booked again, so a retry while routing is down is still the same request, not a conflict.

[cols="2,3,3",options="header"]
|===
| | Modulith | Services

| The call | a method call, same thread | HTTP inside the cluster, not through the gateway
| Who is asking | the planner, in the same security context | the planner's token, passed on; routing checks it again
| Routing is slow | only if its road matrix is (OSRM) | the planner waits at most the timeouts (1 s to connect, 2 s for the answer)
| Routing is down | not possible: it is the same process | the estimate, and a warning in transportation's log
|===

With the straight-line road matrix (the cluster's default), routing's answer and the estimate are the same number: the difference shows only in `distanceSource`. With OSRM configured, `ROUTING` would be the real road network.

[[switch]]
== The switch

`runtime/deploy/implementation.yaml` names the active side. The `ff-implementation` ApplicationSet is a matrix of two git generators: the first reads that file, the second lists `deploy/apps/*` in the repository named after the answer. So the active side's Applications exist and the other side's do not; when the file changes, the ApplicationSet deletes the old ones, and their resources finalizer takes the workloads with them. Switching is one commit, reviewed like any other change.

[mermaid]
....
flowchart LR
  C["commit<br/>implementation.yaml<br/>active: services"] --> AS[Argo CD ApplicationSet]
  AS -->|renders| S1[warehousing] & S2[transportation] & S3[routing] & G[gateway]
  AS -.->|prunes| M[logistics-app]
  G & S1 & S2 & S3 --> DB[("the same tables:<br/>the data stays")]
  G --> SM[smoke test<br/>against the edge]
....

Both sides use the same tables, so the data survives a switch. Each area owns its migrations and its own Flyway history table (`warehousing_flyway_history`, …), whichever process applies them. The same smoke test runs after every switch, against the same URLs.

[[edge]]
== The edge

Port 8081 is a Kubernetes Service named `edge` that selects pods by one label, `ff-logistic/edge: "true"`. On the modulith side, the application's pods carry it. On the services side, only the gateway's pods do, and the gateway routes by path:

[cols="2,2",options="header"]
|===
| Path | Services side

| `/api/v1/wms/**` | warehousing
| `/api/v1/tms/**` | transportation
| `/api/v1/geo/**` | routing
| `/api/v1/me` | transportation (every service answers it the same way)
|===

The edge never changes when the implementation does. The walkthroughs, the smoke test, the load script and later the console all call the edge, and none of them knows which side answered. The edge's own smoke test, run after every switch, signs in through the identity service and calls it the way a client would (xref:walkthrough.adoc[Walkthrough]).
