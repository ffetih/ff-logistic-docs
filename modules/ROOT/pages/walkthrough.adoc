= Walkthrough
:description: Run FF Logistic on either side, and switch between them.

Every walkthrough starts from the edge, `http://localhost:8081`: the same URLs whichever implementation is active. Each sprint adds its part here.

[[picture]]
== The picture to keep in mind

A railway junction. You move one lever, a signalman lays the matching track, and the passengers always arrive at the same platform.

[mermaid]
....
flowchart LR
  L["lever<br/>deploy/implementation.yaml<br/>(one commit)"] --> S["signalman<br/>ApplicationSet ff-implementation<br/>(lays one track, removes the other)"]
  S --> M["modulith track<br/>logistics-app"]
  S -.-> V["services track<br/>gateway + 3 services"]
  M --> P(["platform<br/>edge :8081"])
  V -.-> P
....

* You only ever move the lever: one line in Git.
* The signalman reads it within one to three minutes (it polls Git every 60 s, and Argo CD remembers a branch's head for a while).
* You open the track with `argocd app sync`. Every sync is a journey with an inspection before departure and a check on arrival.
* Clients (curl, the smoke tests, later the console) only know the platform.

What a switch does, step by step, as Argo CD shows it: xref:switching.adoc[Switching sides: what happens].

[[reading-a-sync]]
== Reading a sync: three questions

Every sync prints the same three-part story. Read the HOOK and STATUS columns; the rest is detail.

[cols="1,2,3,1",options="header"]
|===
| Phase | Row | Question | Good answer

| PreSync | `<app>-migrate-…` Job | Is the database ready for this version? | `Succeeded`
| Sync | `Deployment`, `Service` | Is it running? | `Synced`, `Healthy`
| PostSync | `<app>-smoke-test-…` Job | Does it work from outside? | `Succeeded`
|===

The rows with timestamps are the same story, live. Rows for older Jobs are earlier runs, kept a day so their logs can be read.

[cols="1,3",options="header"]
|===
| Word | Means

| Synced / OutOfSync | The cluster matches Git, or does not yet
| Healthy / Progressing / Degraded | It works, it is starting, it is broken
| Missing | In Git, not created yet
|===

[[s1]]
== S1: the skeleton on both sides

What exists: four domain cores with no business yet, one application on each side, the edge, the switch. What it shows: the same request answered by one process or by four, and the database shared between them.

=== Build and import the images

Until CI publishes them (S2), the images are built from the six repositories side by side and imported into the cluster:

[source,bash]
----
cd /mnt/d/dev/workspace/ff-logistic
docs/tools/build-local-images.sh          # base, shared, identity, modulith, services, gateway
----

=== Start on the modulith

`deploy/implementation.yaml` in ff-logistic-runtime says `active: modulith`. After the merge, `ff-root` creates the `edge` and `ff-implementation` Applications; the ApplicationSet creates `logistics-app`.

[source,bash]
----
argocd app sync logistics-app          # PreSync: migrate the three areas; PostSync: its smoke test
argocd app sync edge                   # the edge's smoke test, now with the modulith behind it
----

The order matters: synced before `logistics-app`, the edge's smoke test finds nothing behind the edge and fails, as it should (`FAIL no connection to http://edge:8081 after 30 s`).

Every smoke test first waits, up to 30 seconds, until its Service accepts a connection: a Service created by the same sync (as after every switch) is routable a moment after its pods are ready, and a check that ran into that gap would fail on the network, not on the application. The checks themselves then run once.

Each sync of the edge starts a new smoke-test Job. The latest one's log:

[source,bash]
----
kubectl -n ff-logistics get jobs -l app.kubernetes.io/name=edge-smoke-test \
  --sort-by=.metadata.creationTimestamp -o name | tail -1 | xargs kubectl -n ff-logistics logs
----

----
ok   sign-in as nexus.planner
ok   GET /actuator/health/readiness (none): 200
ok   GET /api/v1/me (none): 401
ok   GET /api/v1/me (token): 200
info the modulith answered: {"git":{"branch":"main","commit":{...}},"build":{"artifact":"logistics-app",...}}
----

[source,bash]
----
curl -s localhost:8081/actuator/info     # the modulith's build and commit
TOKEN=$(curl -s -H 'Content-Type: application/json' \
  -d '{"username":"nexus.planner","password":"fflogistics2026"}' localhost:8085/sessions \
  | sed -n 's/.*"accessToken" *: *"\([^"]*\)".*/\1/p')
curl -s -H "Authorization: Bearer $TOKEN" localhost:8081/api/v1/me
----

=== Switch to the services

[source,bash]
----
cd runtime
sed -i 's/^active: .*/active: services/' deploy/implementation.yaml
git commit -am "Switch to the services" && git push
# within one to three minutes: logistics-app is gone, warehousing, transportation, routing and
# gateway exist. Not waiting: ask the ApplicationSet to read Git now
kubectl -n argocd annotate applicationset ff-implementation argocd.argoproj.io/application-set-refresh=true --overwrite
argocd app list -l ff-logistic/implementation=services
argocd app sync -l ff-logistic/implementation=services
argocd app sync edge
----

The same calls give the same answers; `/actuator/info` now returns 404, because the gateway has no such endpoint, which is how the smoke test tells the two sides apart.

=== What the database says

Each area's history table is shared by both sides: the services found every script already applied by the modulith, and the modulith will find the same when it comes back.

[source,bash]
----
kubectl -n ff-logistics exec deploy/postgres -- psql -U fflogistics -d ff_logistics -c \
  "select 'warehousing' area, version, description, installed_on from warehousing_flyway_history
   union all select 'transportation', version, description, installed_on from transportation_flyway_history
   union all select 'routing', version, description, installed_on from routing_flyway_history order by 1"
----

After the modulith, then the services, the first run gave:

----
      area      | version |        installed_on
----------------+---------+----------------------------
 routing        | 1       | 2026-11-19 23:44:18.352247
 transportation | 0       | 2026-11-19 23:44:18.438579
 transportation | 1       | 2026-11-19 23:44:18.454974
 warehousing    | 0       | 2026-11-19 23:44:18.499055
 warehousing    | 1       | 2026-11-19 23:44:18.512631
----

* Every row is from the same second: the modulith's migration Job. The three services' Jobs ran after the switch, found each area at version 1, and added nothing.
* `routing` came first (areas run in name order) into a database with none of their tables: no baseline. `transportation` and `warehousing` arrived next to it and first recorded a baseline, version 0 (xref:decisions.adoc#d3[decision 3]).

Switch back to `active: modulith` the same way; nothing is migrated twice.

=== Once: the first images

A push doesn't publish a repository's first images: the merge that brings CI in changes `ci.yml`, not an image's folder, so its publish job keeps an image that doesn't exist yet.
Publish them once by hand, in ff-logistic-shared, ff-logistic-modulith and ff-logistic-services: *Actions*, *CI*, *Run workflow* on `main` (or `gh workflow run ci.yml --ref main` inside the repository).
Each run creates its packages on GHCR, private, as every new package is.
The cluster pulls without credentials, so make each public once: GitHub, your profile, *Packages*, the package, *Package settings*, *Change visibility*: `identity`, `logistics-app`, `warehousing`, `transportation`, `routing`, `gateway`.

How CI, Maven and the packages fit together, the `gh` commands, and what went wrong the first time: xref:delivery.adoc[Delivery].

=== Once: from a Deployment to a Rollout

The canary turns each application's `Deployment` into an Argo Rollouts `Rollout`. A plain sync creates the Rollout and leaves the old Deployment running beside it, and both carry the edge label: sync this first time with `--prune`.

[source,bash]
----
argocd app sync logistics-app --prune
kubectl argo rollouts get rollout logistics-app -n ff-logistics --watch   # or the Argo CD UI
----

=== A canary that aborts

[source,bash]
----
# in ff-logistic-modulith: deploy/apps/logistics-app/values-local.yaml, FF_RELEASE_HEALTHY "false"
git commit -am "Break the release on purpose" && git push
argocd app sync logistics-app
----

A values change builds no image (its folder did not change); the new pods are a new revision all the same. The first canary pod answers `DOWN` on `/actuator/health/release`, the analysis fails three times, and the Rollout aborts: the four old pods keep serving, and the edge never sends more than one pod's share to the broken one. Revert the commit and sync to recover.

=== After a change in base or shared

The applications do not see it until their images are built again: in ff-logistic-modulith (and ff-logistic-services) on GitHub, *Actions*, *CI*, *Run workflow*. That run builds on the libraries' latest main and publishes every image (xref:decisions.adoc#d11[decision 11]).

=== The receiving story

A supplier announces a delivery (an ASN: advance shipping notice). When the goods arrive, they are built into pallets; each pallet gets an SSCC, the 18-digit GS1 number printed on its label, and is put away into a bin.

[mermaid]
....
sequenceDiagram
  participant C as curl
  participant W as warehousing<br/>(modulith or service)
  participant D as ff_logistics
  C->>W: POST /api/v1/wms/warehouses (GLN, GS1 company prefix)
  W->>D: wms_warehouses
  C->>W: POST /api/v1/wms/warehouses/{id}/bins
  W->>D: wms_bin_locations
  C->>W: POST /api/v1/wms/asns (lines: GTIN, quantity)
  W->>D: wms_asns, wms_asn_lines (EXPECTED)
  C->>W: POST /api/v1/wms/asns/{id}/pallets (GTIN, quantity, bin)
  W->>D: next value of wms_sscc_serial_seq
  W->>D: wms_pallets (SSCC), the line's received quantity, the ASN's status
  W-->>C: {"sscc": "08690001…", "asnStatus": "RECEIVING"}
....

=== Delivering it

The order of xref:delivery.adoc#order[a sprint's delivery]: *shared* first, then *modulith* and *services*. Their merges change the applications' folders, so the push runs publish new images, built on shared's new main; no *Run workflow* is needed. Merged the other way round, the images would be built on the old cores.

=== After the merge: the first real canary

The S3 images are new versions of running applications, so this is the first sync that goes through the canary steps (S2's first sync created the Rollout, and a new Rollout starts at 100 %).

[source,bash]
----
argocd app sync logistics-app
kubectl argo rollouts get rollout logistics-app -n ff-logistics --watch
----

PreSync migrates warehousing to version 3. Then one pod of four runs the new version (25 %), the analysis asks its release health three times, the Rollout goes to 50 %, waits 30 seconds, and finishes at 100 %.

Each repository was shipped with the helper in xref:delivery.adoc#ship[the Delivery page], which waits for each merge's own run before the next repository starts.

=== Routing talks to transportation

Then the two flows: transportation asks routing for a road leg's distance (flow 1, a question: a method call, or HTTP with a timeout and the straight-line estimate when routing does not answer), and a completed route stop delivers the shipment it carried (flow 3, an event: through the outbox, in-process or over Kafka). Flow 3 can chain into flow 2: a stop completed at a warehouse opens an arrival there, three areas from one click.

The routing service gained an outbox of its own (schema `routing`) and a topic; the transportation service, a consumer. Deliver: shared, then modulith and services, then docs. Deploy on the services side: routing first (it creates the topic), then transportation (it reads it).

Steps and the first run's answers: xref:try-flows.adoc[Try it: routing talks to transportation], with the drill where routing is down.

=== Documents

A shipment's signed e-CMR (a PDF) and a route stop's proof of delivery (a PNG) are stored in RustFS through presigned links: the service signs a slip, the client takes the file straight to the store, and nothing can be written twice (xref:architecture.adoc#documents[how]). Steps, and the three refusals that keep a document written once: xref:try-documents.adoc[Try it: documents, written once].
