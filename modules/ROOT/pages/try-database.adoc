= Try it: a load, with the database away
:description: The modulith under the same five users, with PostgreSQL stopped for half a minute: who waits, what fails, and what is left when it comes back.

xref:try-load.adoc[The load with Kafka away] used the same five users. There the caller did not notice, because a delivery answers from the database commit and the event leaves afterwards. This run takes the database away, so the commit itself has nowhere to go. It was done on the modulith, on 2026-11-22, on the pods that had just finished that Kafka run. The services side has not been measured this way yet.

[[run]]
== How it is started

The modulith was already answering on the edge. Two terminals, both in `runtime`. The drill starts once the load is printing:

[source,bash]
----
deploy/load/run.sh 5 4m 30
----

[source,bash]
----
deploy/load/drill.sh postgres 30
----

The load is the same scenario: plan, read, pick up, depart, deliver, warehouses, distance. The drill scales the `postgres` deployment to zero, waits, and scales it back to one. While the pod is gone the drill cannot count, because its counts are queries. A line then says `the database does not answer`.

[[caller]]
== What the caller saw

The load started at 05:03:31Z. The drill started fifteen seconds later, during the warm-up. The measured four minutes include the outage.

[source]
----
side: modulith  vus: 5  warm-up: 30s  measured: 4m
iterations: 877  (3.65/s)  requests: 6114  (25.5/s)  failed: 0.08%
request      count  failed  med ms  p95 ms  p99 ms  max ms
sign-in          5    0.0%    69.8    76.6    77.3    77.4
plan           877    0.6%    12.2    34.4 23293.3 30032.5
shipment       872    0.0%     3.2    13.6    21.0   254.3
pickup         872    0.0%     9.2    21.4    32.2    59.1
departure      872    0.0%     9.7    20.3    25.0   173.4
deliver        872    0.0%    10.3    19.0    22.9    29.8
warehouses     872    0.0%     2.7     5.7     8.0    21.9
distance       872    0.0%     1.3     2.7     3.6    19.3
----

Only `plan` failed, five times: 877 plans, and 872 of every later request. An iteration that fails to plan does not go on, so those five shipments were never picked up or delivered. The median stayed 12.2 ms and the p95 stayed 34 ms, the same band as the Kafka run. The p99 is 23.3 s and the slowest plan is 30.0 s. A plan either got a connection and finished as usual, or it waited until the database came back, or it gave up at 30 s.

The rate fell from 4.71 iterations a second, on the Kafka run, to 3.65. The missing iterations are that waiting. Five users, each held for about half a minute, is a few hundred iterations over four minutes.

[[blind]]
== What the drill could see

[source]
----
== drill: postgres away for 30s, modulith side, from 2026-11-22T05:03:46Z
  time  postgres  delivered  arrivals analytics  outbox
   +1s  up                0         0         5       3
  +66s  away      (the database does not answer)
-- postgres back at +66s
  +67s  back      (the database does not answer)
  +73s  back              7        11         5       0
-- caught up 7s after postgres came back
----

The argument was 30 s. The file has one `away` line, at +66 s, and the deployment was scaled back at that same moment. The sample is a `kubectl exec` into `deploy/postgres`. While the pod is gone that call does not return, so the loop's 30 s are only counted between samples. One sample filled the whole window. The database was scaled to zero for about a minute, and it accepted a query again at +73 s. The new pod is `postgres-986699bff-vrmdp`.

Caught up, on the first sample that could read. Delivered 7, arrivals 11, analytics 5, outbox 0. The drill allows three in flight, and the four figures are four queries in a row, so arrivals a few ahead of delivered is the load moving between them. The outbox was empty: a plan that failed had committed nothing, and a plan that waited committed, opened its arrival in-process, and had its events taken. Nothing was left unpublished, and nothing had to be replayed.

[[pods]]
== What the pods cost

At rest, before this run, the four `logistics-app` pods held 1847 MiB. The Kafka run had left them at 1835 MiB under load, and they had not shrunk. This is not a cold measurement. CPU was 10 millicores.

Under load the highest sample was 639 millicores and 1969 MiB. Lower CPU than the Kafka run's 1044, because the users spent part of the four minutes waiting rather than sending. Kafka's highest sample was 60 millicores. There was no backlog for it to drain.

[[shown]]
== What this run shows

* *The caller feels a database that is away, and only at the plan.* Five plans failed at 30 s. Every request after a successful plan succeeded, including the delivery. With Kafka away, nothing failed.
* *There is no queue to catch up.* Kafka left an outbox that drained for minutes. Here the first readable sample was already within the drill's margin, seven seconds after the pod was scaled back.
* *The drill's 30 s is not the outage.* Its own query blocks while the pod is gone, and the recorded gap was about a minute. The services side has not been run.
