= Decisions
:description: Why FF Logistic is built the way it is, and what each choice costs.

Each decision records the problem, the choice, what it costs, and what else was considered. A decision is changed by writing what replaced it, not by deleting it.

[[d1]]
== 1. Three layers: runtime, shared, implementations

Problem:: Two implementations of one product invite two copies of everything around it: two identity services, two analytics pipelines, two clusters. The comparison would then measure the copies.
Decision:: *runtime* is what we run but do not write. *shared* is what we write once and that does not care which implementation runs. *modulith* and *services* hold only what is genuinely different.
Costs:: Six repositories. A change that crosses layers (a new event field) is several pull requests.
Considered:: One repository with folders: simpler to change, but it hides the boundaries that the comparison is about, and every build builds everything.

[[d2]]
== 2. The business rules exist once, as domain cores with ports

Problem:: Written twice, the rules drift, and a measured difference may come from the drift instead of from the architecture.
Decision:: Each area (standards, warehousing, transportation, routing) is a jar in `shared`. A core may depend on `standards` only; what it needs from another area is a port (an interface or an event). The modulith and the services provide the adapters.
Costs:: The services side gets a little more ceremony than a services-only design would have.
Checked:: A spike (S01-01, `spikes/modulith-modules-from-jars` in ff-logistic-docs) showed that Spring Modulith finds modules by package, wherever the class files are: a core in a jar is a module, its `package-info.java` is honoured, and an adapter placed in the modulith's jar under a core's package counts as part of that module. A call into another module's internals, a dependency not allowed, and a cycle each fail `verify()`. Two guards keep a core clean: Maven at compile time (a core depends on `standards` only) and Spring Modulith in the modulith's tests (adapters use other areas through their API only, and nothing forms a cycle).
Considered:: Two independent codebases: a cleaner story for each side, twice the rules. Cores inside the modulith repository: the fallback, had the spike failed.

[[d3]]
== 3. One database, the same tables; each area owns its migrations

Problem:: With separate databases per implementation, a switch would start from empty data, and the two sides could never be checked against the same rows.
Decision:: Both sides use `ff_logistics` and the same tables. Each area keeps its migrations under `db/migration/<area>` with its own Flyway history table, `<area>_flyway_history`. The modulith runs four migrations, one per area; each service runs its own.
Costs:: Both sides must agree on the schema exactly, by construction (the migrations are in the cores). The second area to arrive in the database finds the others' tables and starts its history with a baseline row (version 0); that is Flyway's way of accepting a schema it does not own alone. The services side does not get a database per service, the textbook setup; here the areas are separated by table ownership instead. Database roles per area can enforce that later.
Considered:: A schema per area: closer to database-per-service, and possible later without changing the cores' code.

[[d4]]
== 4. Exactly one implementation is active; the switch is a commit

Problem:: Running both at once doubles the events on the shared topics and the writers on the shared tables.
Decision:: `runtime/deploy/implementation.yaml` names the active side; an ApplicationSet renders only that side's Applications and prunes the other.
Costs:: Side-by-side latency comparisons need two runs, not one.
Considered:: Both sides at once with separate databases and topic prefixes: rejected with decision 3.

[[d5]]
== 5. One edge, selected by a label

Problem:: Clients must not care which side answers.
Decision:: The Service `edge` (port 8081) selects `ff-logistic/edge: "true"`. The modulith's pods carry the label; on the services side only the gateway's pods do, and the gateway routes by path prefix.
Costs:: One more hop on the services side, which is real and is measured.
Considered:: Spring Cloud Gateway instead of nginx: more features than a path table needs.

[[d6]]
== 6. One outbox for both: the Spring Modulith event registry

Problem:: A service that commits to its database and then sends to Kafka can lose the event between the two (the dual-write problem).
Decision:: Both sides record events in the Spring Modulith event publication registry, in the same transaction as the change, and externalize them to Kafka after commit. The services use only the registry and the Kafka externalization, not the module model.
Costs:: Consumers see each event at least once and must be idempotent; across keys the order is not guaranteed, so consumers order by `occurredAt`.
Considered:: Debezium change data capture: another moving part for the same guarantee.

[[d7]]
== 7. The flows between areas are designed in

Problem:: In the earlier version, the areas hardly talked to each other; with no flows between them, both implementations would behave the same.
Decision:: Three flows, a query and two events (xref:architecture.adoc#flows[Architecture]), each through a port.
Costs:: Business logic that the earlier version did not have.

[[d8]]
== 8. Deploy values live next to the code

Problem:: If CI in `shared` builds an image whose tag lives in `runtime`, CI must write to another repository, which the built-in GitHub token cannot do.
Decision:: Runtime holds the chart and the Argo CD Applications; the values, the image tag included, live in the repository that builds the image. The Applications are multi-source.
Costs:: An Application's definition and its values are in two places.

[[d9]]
== 9. The documentation: a hub, and a component per repository

Problem:: Docs in one central repository drift away from the code they describe; docs spread over six repositories have no front page.
Decision:: A doc lives where the change that makes it wrong happens. What spans repositories (plan, architecture, decisions, comparison) lives in `ff-logistic-docs`; the rest lives with its code. Antora assembles one site from all six.
Costs:: Diagrams render through Kroki, since Antora runs Asciidoctor.js, which cannot run PlantUML locally.

[[d10]]
== 10. Mermaid in the hub

Problem:: The hub is read on GitHub as much as on the site.
Decision:: The hub's diagrams are Mermaid, which GitHub renders in Markdown and Kroki renders in the site. The components may keep PlantUML, also through Kroki.

[[d11]]
== 11. CI: written once, the libraries built from source

Problem:: Five repositories build Java the same way, and four of them build on base (and shared) that live in other repositories. Copying one workflow into each would drift; publishing the libraries to a Maven registry would need a token for every reader, even of public packages (GitHub Packages).
Decision:: Two reusable workflows in ff-logistic-runtime, `java-build.yml` and `java-publish.yml`; each repository's `ci.yml` only names what it builds on and which images it publishes. The libraries are cloned from main and installed before the build, without their tests (their own CI runs those). An image is rebuilt only when its folder or the build files changed; its tag is committed to the same repository (xref:#d8[decision 8]).
Costs:: A change in base or shared does not rebuild the applications by itself: their CI has a "Run workflow" button that publishes every image. Every build compiles the libraries again (about a minute). The libraries have no versions of their own: an application always builds on main.
Considered:: GitHub Packages for the jars, with versions: right for libraries other teams depend on, a token in every clone here. A dispatch from base to the applications' CI: needs a personal access token stored as a secret in base.

[[d12]]
== 12. Each process keeps its outbox in a schema of its own

Problem:: The services share one database (xref:#d3[decision 3]). Spring Modulith's event publication registry keeps the outbox in one table, `event_publication`. Shared by three services, a service that restarts would find the others' unfinished events among its own, and could publish them again, from the wrong process.
Decision:: Every process that publishes events keeps its registry in a schema named after it: `modulith.event_publication` in the modulith, `transportation.event_publication` in the transportation service. The table is migrated like an area (`outbox`, with its history in the same schema), by a library written once, ff-base-events, which also keeps the outbox: unfinished events published again from one pod at a time (a PostgreSQL advisory lock named after the schema), with a doubling wait and a maximum of attempts, and completed rows deleted after a week. A process names its schema once, `ff.events.schema`; the registry's settings follow from it.
Costs:: Two more schemas in the database. A switch leaves the other side's unfinished rows where they are: they are picked up when that side is active again. The business tables stay in the shared schema, unchanged.
Considered:: One table per service in the shared schema (`transportation_event_publication`): no schema, but a table name to configure per process, and no natural place for its history. One shared table with a column for the process: the registry has no such column.

[[d13]]
== 13. Staying with six repositories

Problem:: In S5 a change crossed four repositories (Timefold's version in base, the core in shared, the settings in both implementations). They had to be merged in order, each waiting for the one before (xref:delivery.adoc#ship[ship]). Decision 1 named this cost; after five sprints, is it still worth paying?
Decision:: Yes: stay with six repositories, and make the delivery cheaper instead of the structure simpler. The boundaries are what the comparison is about: two implementations that cannot reach into each other's code make it believable, where folders in one repository would need discipline and tools to stay apart. The repositories also stand for the parts of an organisation (a platform, libraries, domain teams), and several decisions (8, 9, 11) exist because of them.
Costs:: A sprint across repositories is several pull requests, merged in order. One front door is needed, so a reader does not meet six repositories at once: this site, linked from every README.
Considered:: Merging into one repository, keeping each history (`git subtree`): one pull request per change, the build order handled by Maven; about a sprint of work on CI, Argo CD paths and the site, and the boundaries become conventions. To be reconsidered if, with the delivery automated, it still costs more than the features.

[[d14]]
== 14. Event contracts as example messages in shared

Problem:: In S6 the modulith starts sending the events the services send, and a reader outside both, the analytics loader, must not be able to tell them apart. Both sides serialize the same shared records today, so they agree; nothing keeps them agreeing when a field, a type or a key changes on one side.
Decision:: A small library in shared, `ff-contracts`: one file per topic with an example message, the field the message is keyed by, the fields that may be `null`, and the formats of the fields a reader parses (`uuid`, `instant`). `EventContract.verify(key, message)` lists everything wrong with a message. Every producer's test, in the modulith and in each service, sends a real event through a broker in its JVM, reads it back and verifies it; the loader's test parses the same example. A message must have exactly the contract's fields: a new field goes into the contract first.
Costs:: A field is written in two places, the record and the contract. Old messages on a topic are not checked: the contract describes what is sent from now on.
Considered:: A schema registry (Avro or JSON Schema with Confluent's or Apicurio's): checks at send time and versions the schemas, but one more service to run, and every client gains a serializer and a registry address. Pact, consumer-driven contracts: a broker for the pacts and a verification step per pair; fits many teams and many readers, more than one loader and two producers. Comparing the two sides' messages in one test: no build has both sides in it.
